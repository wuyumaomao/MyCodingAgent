# Claude Code / Claude API: Context Management & Memory

✅ = Anthropic primary source. ⚠️ = secondary/inference. `platform.claude.com/docs` would not render for me, so memory-tool/context-editing specifics come from Anthropic's own cookbooks.

## 1. AUTO-COMPACT, `/compact`, `/context`
- **Trigger:** Claude Code "compacts when the conversation reaches the model's context limit," clearing older tool outputs first and summarizing if needed ✅ [model-config](https://code.claude.com/docs/en/model-config#default-auto-compact-thresholds), [how-claude-code-works](https://code.claude.com/docs/en/how-claude-code-works#when-context-fills-up). 200K models compact at the 200K boundary; native-1M models (Sonnet 5, Fable, Opus 4.7+) "at about 967K tokens by default" ✅. Tunable: `/autocompact 500k`, `--autocompact`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW` ✅ [model-config](https://code.claude.com/docs/en/model-config#set-the-auto-compact-window).
- **Mechanism:** an LLM-written summary replacing earlier turns — a *separate request* with the same system prompt, tools and history plus a summarization instruction as a final user message ✅ [prompt-caching](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation).
- **Preserved:** requests/intent, key concepts, files read or modified with snippets, errors and fixes, pending tasks, current work; project-root CLAUDE.md, auto memory, the plan, and *up to five* most recently modified files are re-injected; invoked skill bodies return, but the skill *listing* does not reload ✅ [context-window](https://code.claude.com/docs/en/context-window#what-survives-compaction).
- **Manual:** `/compact` takes focus instructions, e.g. `/compact focus on the auth bug fix` ✅ (above); `/clear` between tasks ✅ [commands](https://code.claude.com/docs/en/commands). **`/context`** shows usage as a colored grid with optimization suggestions (context-heavy tools, memory bloat, capacity warnings) ✅ (same). Auto-compaction halts with a "thrashing" error if context refills immediately after each summary ✅ [troubleshooting](https://code.claude.com/docs/en/troubleshooting#auto-compaction-stops-with-a-thrashing-error).

## 2. CLAUDE.md MEMORY HIERARCHY
- **Load order, broadest → most specific:** managed policy (`/etc/claude-code/CLAUDE.md`; `C:\Program Files\ClaudeCode\CLAUDE.md`) → user `~/.claude/CLAUDE.md` → project `./CLAUDE.md` or `./.claude/CLAUDE.md` → local `./CLAUDE.local.md` ✅ [memory](https://code.claude.com/docs/en/memory#choose-where-to-put-claude-md-files).
- **Concatenated, not overriding.** Ancestors of the cwd load at launch, root → cwd (closest read last), with `CLAUDE.local.md` after `CLAUDE.md` per level ✅ [memory](https://code.claude.com/docs/en/memory#how-claude-md-files-load).
- **Both parent and child load, differently:** ancestors at launch; subdirectory files load **on demand** when Claude reads files there ✅ (same). Files up to 4 MiB load whole, larger are skipped; target <200 lines ✅.
- **Imports:** `@path`, resolved relative to the importing file, recursion max **4 hops**, ignored inside code spans/fences, backticks keep a path literal. Imports outside the working directory need a one-time approval, and importing saves no context ✅ [memory](https://code.claude.com/docs/en/memory#import-additional-files).
- Auto memory is separate: `~/.claude/projects/<project>/memory/MEMORY.md`, first 200 lines or 25KB loaded ✅ [memory](https://code.claude.com/docs/en/memory#auto-memory).

## 3. MEMORY TOOL + CONTEXT EDITING
- **Memory tool** (`memory_20250818`): file-based under `/memories`; ops `view`, `create`, `str_replace`, `insert`, `delete`, `rename`; **the client implements it** — "client-side implementation gives you full control" ✅ [memory cookbook](https://platform.claude.com/cookbook/tool-use-memory-cookbook), [context-engineering cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools); doc: [memory-tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool).
- **Why client-side:** Anthropic describes a client-side file system giving developers control of their data while the model decides what to store and when to retrieve ⚠️ ([ZenML summary of Anthropic's talk](https://www.zenml.io/llmops-database/building-production-agentic-systems-with-platform-level-llmops-features)). Inference: the API keeps no memory state — memory is a tool schema plus files you own.
- **Context editing** (server-side): `clear_tool_uses_20250919` — trigger default **100K** input tokens, `keep` default **3** tool uses, plus `clear_at_least`, `exclude_tools`, `clear_tool_inputs`; `clear_thinking_20251015` for thinking blocks ✅ [cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools). It is *sub-transcript*: it replaces `tool_result` payloads with a placeholder while keeping the `tool_use` record ✅ (same); doc: [context-editing](https://platform.claude.com/docs/en/build-with-claude/context-editing).
- **Savings:** **84%** fewer tokens in a 100-turn web-search eval; editing alone **+29%** task performance, **+39%** with the memory tool ⚠️ — the [blog post](https://claude.com/blog/context-management) would not render for me; figures come from secondary summaries ([chanl](https://www.channel.tel/blog/agent-context-editing-memory-tool-token-cost), [ZenML](https://www.zenml.io/llmops-database/building-production-agentic-systems-with-platform-level-llmops-features)). Server-side compaction (`compact_20260112`) defaults to a 150K trigger, min 50K ✅ (cookbook).

## 4. WHAT MAKES COMPACTION ROBUST
- Add a **"Compact Instructions"** section to CLAUDE.md, or pass a focus to `/compact` ✅ [how-claude-code-works](https://code.claude.com/docs/en/how-claude-code-works#when-context-fills-up). The compactor reads CLAUDE.md like any context and "matches on intent, so the section header is free-form" ✅ [agent-loop](https://code.claude.com/docs/en/agent-sdk/agent-loop#automatic-compaction).
- Documented preserve-list example: task objective and acceptance criteria; file paths read or modified; test results and error messages; decisions and their reasoning ✅ (same).
- Anthropic engineering: compaction "preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs," continuing with "the five most recently accessed files"; tune by "maximize recall first... then iterate to improve precision" ✅ [effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). The literal compaction prompt is **not published** ⚠️.

## 5. SUBAGENTS / CONTEXT ISOLATION
- Each subagent runs in **its own context window** with its own system prompt, tools and permissions; it never sees the parent conversation, and only its final report plus a small metadata trailer returns — the docs' example: 6,100 tokens of reads → 420 tokens back ✅ [sub-agents](https://code.claude.com/docs/en/sub-agents), [context-window](https://code.claude.com/docs/en/context-window).
- Startup context: own prompt, delegation task message, full CLAUDE.md hierarchy, git-status snapshot, preloaded skills; **not** the main session's auto memory or output style. Explore/Plan skip CLAUDE.md ✅ (same).
- Subagent transcripts are separate files, unaffected by main-conversation compaction ✅ — but many subagents each returning detail still consume context ✅. In the Agent SDK, only the final response returns "as a tool result" ✅ [agent-loop](https://code.claude.com/docs/en/agent-sdk/agent-loop#keep-context-efficient).

## 6. PROMPT CACHING
- Requests are ordered **system prompt → project context (CLAUDE.md, auto memory, unscoped rules) → conversation**, matched as an exact prefix, so a change anywhere invalidates everything after it; compaction "by design... invalidates the conversation layer," while the system-prompt layer is reused and project context reloads from disk ✅ [prompt-caching](https://code.claude.com/docs/en/prompt-caching#how-the-cache-is-organized).
- The summarization request shares the prefix, so a mid-session `/compact` "costs a fraction of what the context size suggests"; after TTL expiry or when resuming an old session it reprocesses full history uncached ✅ [prompt-caching](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation).
- Tool definitions sit in the system-prompt layer: deferred MCP tools append without invalidating, prefix-loaded ones invalidate when the tool set changes ✅ [prompt-caching](https://code.claude.com/docs/en/prompt-caching#connecting-or-disconnecting-an-mcp-server). Editing CLAUDE.md mid-session keeps the cache but doesn't apply until `/clear`, `/compact`, or restart ✅ [prompt-caching](https://code.claude.com/docs/en/prompt-caching#editing-claude-md-mid-session). Subagents warm their own cache; forks read the parent's.

## 7. WHAT IS *NOT* MEMORY
- The conversation is not persisted memory: "Each Claude Code session begins with a fresh context window," and sessions are independent, "without the conversation history from previous sessions" ✅ [memory](https://code.claude.com/docs/en/memory), [how-claude-code-works](https://code.claude.com/docs/en/how-claude-code-works#work-with-sessions).
- Transcripts *are* written to `~/.claude/projects/` JSONL for resume, fork and rewind — session persistence for *you*, not context the model automatically has ✅ (same).
- Only files carry knowledge across sessions: CLAUDE.md and auto memory (machine-local, shared per git repo) ✅ [memory](https://code.claude.com/docs/en/memory#auto-memory). "Claude remembers our chat" is false unless it was written to a file; and the context window is working memory, not memory — context rot degrades recall as it fills ✅ [effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

## DESIGN PRINCIPLES OBSERVED
- **Context is a finite attention budget, not storage** — the levers are compaction, clearing and isolation, not just larger windows.
- **Persist only what can't be re-derived**, in files (CLAUDE.md, `/memories`) rather than trusting conversation history.
- **Order operations by cost:** cheap structural clearing of tool results first; lossy summarization only when the window demands it.
- **Prefix stability is a first-class constraint** — cache invalidation shapes when compaction, model switches and CLAUDE.md edits may happen.
- **Isolate by default:** subagents and external memory exist so the main window keeps only high-signal tokens; what returns is a summary, not a transcript.
